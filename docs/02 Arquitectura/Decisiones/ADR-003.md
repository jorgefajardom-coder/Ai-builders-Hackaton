# ADR-003 — Corpus grabado + tester diferencial como columna vertebral

## Contexto
Hay que entender un servicio sin documentación, demostrar con evidencia cada regla de la spec, llevar un log de experimentos y saber en todo momento qué tan parecido es el reemplazo. Además, a mitad del día habrá un incidente que puede cambiar el comportamiento.

## Decisión
Todo sondeo al original pasa por un **prober propio** que hace `reset` → secuencia → y graba cada request/response en un **corpus JSONL versionado**. Un **tester diferencial** reproduce las mismas secuencias contra el reemplazo y compara. El corpus se divide en:
- **Desarrollo:** lo que vemos para escribir la spec.
- **Hold-out:** secuencias generadas con otra semilla del fuzzer que **no miramos**; simulan el set oculto.

## Alternativas descartadas
| Alternativa | Por qué la descartamos |
|---|---|
| Exploración manual con curl/Postman | Sin rastro reproducible: no alimenta el log ni la spec, y no sirve para regresiones ni para detectar el incidente |
| Herramientas que generan specs o clones automáticamente | Prohibidas por las reglas ("hacen el trabajo por ti"). Fuzzer y scripts propios sí están permitidos |
| Medir solo con el corpus de desarrollo | Sobreajuste: el set oculto corre sobre algo que no hemos visto. El hold-out estima la generalización |

## Consecuencias
- **Ganamos:** cada regla tiene evidencia; métrica de paridad continua; detección del incidente por diff; el log de experimentos se escribe solo.
- **Perdemos / riesgos:** cuesta construir el banco de pruebas antes de ver resultados (~1 h). Si el original tiene rate limit, hay que dosificar el fuzzing.
- **Cómo lo medimos:** es el propio mecanismo de medición → [[Plan de evaluación]].
