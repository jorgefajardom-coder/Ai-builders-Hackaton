# ADR-001 — Catch-all HTTP de bajo nivel en vez de routing de framework

## Contexto
El reemplazo debe responder **exactamente** como el original, incluidas las rutas inexistentes, los métodos no permitidos y los errores de validación. Los frameworks web modernos responden por su cuenta en esos casos: 404/405 con su propio formato, redirects por la `/` final, 422 de validación automática, manejo implícito de `HEAD`/`OPTIONS`, y headers y serialización JSON propios.

## Decisión
Un **único handler catch-all** que recibe todo (cualquier método y ruta) y un **router propio** que decide cada respuesta. Escribimos status, headers y **bytes** del body a mano. Sin validación automática ni serialización implícita.

Lenguaje: **por decidir** → opciones abajo.

## Alternativas descartadas
| Alternativa | Por qué la descartamos |
|---|---|
| FastAPI/Express con rutas declarativas y validación de modelos | Generan respuestas que no controlamos (422, 404 y 405 propios, orden de claves, espacios). Cada una sería un punto de no-paridad que hay que parchear |
| Proxy o grabación con replay literal (devolver la respuesta grabada más parecida) | No generaliza a entradas no vistas ni a estado nuevo; el set oculto "corre sobre algo que no han visto" |

## Opciones de lenguaje
| Opción | A favor | En contra |
|---|---|---|
| **Python + Starlette/ASGI crudo** (o `aiohttp` low-level) | Mismo lenguaje que el banco de pruebas; iteración rápida | Hay que desactivar con cuidado las respuestas automáticas |
| **Node + `http` nativo** | Control total del byte; sin magia | Dos lenguajes en el repo |
| **Go `net/http`** | Control total, binario único, despliegue simple | Iteración más lenta en 8 h |

## Actualización con el README
El set **no compara headers** y compara JSON **sin importar el orden de las claves**. Eso baja el riesgo de la serialización: basta con un JSON correcto, sin igualar byte a byte. Sigue siendo crítico controlar **status + body** de las rutas inexistentes, los métodos no permitidos y los cuerpos que no son JSON (ahí se compara el texto exacto). La decisión del catch-all se mantiene; la del serializador manual se relaja.

## Consecuencias
- **Ganamos:** control total de la paridad; ningún comportamiento "regalado" por el framework.
- **Perdemos / riesgos:** más código manual (parseo de body, routing). Hay que probar que el servidor HTTP subyacente no altere los headers.
- **Cómo lo medimos:** paridad en las categorías 404/405/body malformado del [[Plan de evaluación]].
