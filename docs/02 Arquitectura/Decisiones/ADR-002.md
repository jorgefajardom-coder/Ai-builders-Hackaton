# ADR-002 — Estado en memoria, una sola instancia

## Contexto
El original tiene estado (existe `/__reset`). El evaluador llama `/__reset` antes de **cada** test, así que no necesitamos durabilidad entre tests. Sí necesitamos consistencia: dos requests seguidos deben ver el mismo estado.

## Decisión
Estado en **memoria del proceso**, con un snapshot del estado inicial que `/__reset` restaura (deep copy). **Una sola instancia y un solo worker.** Un lock alrededor de cada request para serializar el acceso.

## Alternativas descartadas
| Alternativa | Por qué la descartamos |
|---|---|
| Redis / Postgres / SQLite | Agrega latencia, infraestructura y un punto de falla, sin beneficio: el estado se reinicia en cada test |
| Varias instancias con estado compartido | Varias instancias con estado local darían respuestas inconsistentes; compartirlo exige una base de datos (ver arriba). La carga del evaluador no lo justifica |

## Consecuencias
- **Ganamos:** simplicidad, latencia mínima, reset trivial y determinista.
- **Perdemos / riesgos:** si el hosting reinicia el proceso, el estado se pierde (aceptable: el test empieza con reset). Hay que **fijar 1 instancia y 1 worker** en el hosting; un autoscaling silencioso rompería la paridad.
- **Cómo lo medimos:** tests de secuencia (T-seq-*) en el [[Plan de evaluación]].
